# Python Advanced Framework Patterns — AI Slop Reference

Framework-specific anti-patterns generated by AI in SQLAlchemy, Flask, FastAPI, Celery, and pytest.
Each entry has a risk score (1 = trivial style, 5 = silent data loss or security hole), before/after code,
and safety checks to run before applying the fix.

---

## SQLALCHEMY ORM PATTERNS

### 1. N+1 Queries — Loading Relationships in Loops
**Risk: 4**
**Smell:** AI fetches a list of parent objects, then accesses a relationship attribute inside a loop,
firing one SELECT per row instead of a JOIN.
**Fix:** Declare the load strategy at query time with `joinedload` (for many-to-one / one-to-one) or
`selectinload` (for one-to-many / many-to-many collections).
**Safety checks:**
- Confirm the relationship exists in the ORM model before adding a loader option.
- Use `selectinload` for collections (avoids cartesian product); use `joinedload` for singular relations.
- Add `SQLALCHEMY_ECHO=True` in dev to see query counts before/after.

```python
# BEFORE — N+1: 1 query for orders + 1 per order for user
orders = session.execute(select(Order)).scalars().all()
for order in orders:
    print(order.user.email)   # each access fires a lazy SELECT

# AFTER — 2 queries total (orders + a batched IN for users)
from sqlalchemy.orm import selectinload

orders = session.execute(
    select(Order).options(selectinload(Order.user))
).scalars().all()
for order in orders:
    print(order.user.email)   # already loaded, no extra query

# AFTER (many-to-one scalar) — single JOIN query
orders = session.execute(
    select(Order).options(joinedload(Order.user))
).scalars().unique().all()
```

### 2. Lazy Loading in Async Context (MissingGreenlet)
**Risk: 5**
**Smell:** SQLAlchemy async session with ORM models that use the default `lazy="select"` strategy.
Accessing a relationship outside an awaited call raises `sqlalchemy.exc.MissingGreenlet` at runtime.
**Fix:** Use `lazy="raise"` on all relationships to make the error explicit, and always load eagerly
in async code.
**Safety checks:**
- Every relationship in an async model must be either `lazy="raise"` or loaded via `selectinload`/`joinedload`.
- `lazy="raise_on_sql"` is a gentler alternative (allows already-loaded access).
- Never access unloaded attributes after `await session.commit()` — they expire by default.

```python
# BEFORE — blows up at runtime in async context
class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user: Mapped["User"] = relationship()  # default lazy="select"

async def get_order(session: AsyncSession, order_id: int) -> Order:
    order = await session.get(Order, order_id)
    print(order.user.email)   # MissingGreenlet — cannot lazy load here
    return order

# AFTER — fail loudly at definition time, load explicitly
class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user: Mapped["User"] = relationship(lazy="raise")   # loud at access time

async def get_order(session: AsyncSession, order_id: int) -> Order:
    order = await session.execute(
        select(Order)
        .where(Order.id == order_id)
        .options(selectinload(Order.user))
    )
    return order.scalar_one()
```

### 3. Session Management — Wrong Scope, Unclosed Sessions
**Risk: 5**
**Smell:** AI creates a `Session` at module level, inside a function without a context manager,
or opens a session per request but forgets to close it. Causes connection pool exhaustion and
stale data across requests.
**Fix:** Use a context manager (`with Session(engine) as session`) or a scoped session factory
tied to the request lifecycle.
**Safety checks:**
- Never store a bare `Session` in a module-level variable.
- In web apps, session lifecycle must match request lifecycle.
- `Session.close()` must be in a `finally` block if not using a context manager.

```python
# BEFORE — module-level session, never closed
engine = create_engine(DATABASE_URL)
session = Session(engine)   # shared across all requests

def get_user(user_id: int) -> User:
    return session.get(User, user_id)

# BEFORE — function-scoped session without cleanup
def create_user(data: dict) -> User:
    session = Session(engine)
    user = User(**data)
    session.add(user)
    session.commit()
    return user   # session leaked

# AFTER — context manager per unit of work
from sqlalchemy.orm import Session

def get_user(user_id: int) -> User:
    with Session(engine) as session:
        return session.get(User, user_id)

# AFTER — FastAPI / Flask: session per request via factory
def get_session() -> Generator[Session, None, None]:
    with Session(engine) as session:
        yield session
        # session.close() called automatically on context exit
```

### 4. `session.query()` (Legacy Style) vs `select()` (2.0 Style)
**Risk: 2**
**Smell:** AI consistently generates the SQLAlchemy 1.x `session.query(Model).filter(...)` API.
This still works but is deprecated in 2.0 and removed from the async session entirely.
**Fix:** Use `select()` + `session.execute()` everywhere.
**Safety checks:**
- `session.query()` does not work with `AsyncSession` — this is a hard breakage.
- If the codebase mixes both styles, standardise to 2.0 in one pass.
- `scalar_one()`, `scalars().all()`, `one_or_none()` replace the old result accessors.

```python
# BEFORE — 1.x legacy query API
users = session.query(User).filter(User.active == True).all()
user  = session.query(User).filter_by(email=email).first()
count = session.query(func.count(User.id)).scalar()

# AFTER — 2.0 select() style
from sqlalchemy import select, func

users = session.execute(select(User).where(User.active == True)).scalars().all()
user  = session.execute(select(User).where(User.email == email)).scalar_one_or_none()
count = session.execute(select(func.count(User.id))).scalar()
```

### 5. Bulk Operations — `session.add()` in a Loop
**Risk: 4**
**Smell:** AI wraps bulk inserts or updates in a `for` loop calling `session.add()` once per object.
This fires one INSERT per row and holds all objects in the identity map, consuming memory and time.
**Fix:** Use Core-level `insert()` with `session.execute()` for bulk inserts, or `bulk_insert_mappings`
for ORM objects when you need defaults populated.
**Safety checks:**
- Core `insert()` bypasses the ORM identity map and event listeners — confirm no `@event.listens_for`
  hooks need to run (e.g., `after_insert`).
- `bulk_insert_mappings` does not call `__init__` or validators.
- Return the inserted IDs only if truly needed; otherwise skip `returning()`.

```python
# BEFORE — 10,000 INSERTs in a loop
records = [{"name": f"User {i}", "email": f"u{i}@x.com"} for i in range(10_000)]
for r in records:
    session.add(User(**r))
session.commit()

# AFTER — single batched INSERT (Core style, fastest)
from sqlalchemy import insert

session.execute(insert(User), records)
session.commit()

# AFTER — ORM bulk if you need server defaults / event hooks
session.bulk_insert_mappings(User, records)
session.commit()
```

### 6. Missing Indexes on FK Columns and Query Columns
**Risk: 4**
**Smell:** AI defines foreign keys with `ForeignKey(...)` but omits `index=True`. Also omits indexes
on columns that appear in `WHERE`, `ORDER BY`, or `JOIN` conditions. Causes full-table scans at scale.
**Fix:** Add `index=True` to all FK columns. Add explicit `Index(...)` for multi-column or
partial indexes needed by known query patterns.
**Safety checks:**
- Adding indexes to an existing table requires a migration — use `alembic` and ensure the index
  is created `CONCURRENTLY` in Postgres to avoid table locks.
- Do not over-index write-heavy tables (each index slows INSERT/UPDATE).
- Composite indexes must have the highest-selectivity column first.

```python
# BEFORE — FK with no index; full scan on order lookups by user
class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))  # no index
    status: Mapped[str] = mapped_column(String(20))               # often filtered
    created_at: Mapped[datetime] = mapped_column(DateTime)

# AFTER — index FK and query columns
from sqlalchemy import Index

class Order(Base):
    __tablename__ = "orders"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"), index=True)
    status: Mapped[str] = mapped_column(String(20))
    created_at: Mapped[datetime] = mapped_column(DateTime)

    __table_args__ = (
        # composite index for "all open orders by user, newest first"
        Index("ix_orders_user_status_created", "user_id", "status", "created_at"),
    )
```

### 7. `expire_on_commit=True` Causing Lazy Load After Commit
**Risk: 4**
**Smell:** Default SQLAlchemy behaviour expires all ORM attributes after `session.commit()`.
AI code that accesses an attribute on a committed object triggers a new SELECT — or raises
`DetachedInstanceError` if the session is closed.
**Fix:** Either access needed attributes before closing the session, use `expire_on_commit=False`
where safe, or refresh explicitly.
**Safety checks:**
- `expire_on_commit=False` means stale data can linger if the same session is reused across
  multiple transactions — only safe with short-lived, request-scoped sessions.
- `session.refresh(obj)` is the explicit, safe alternative when you need fresh state.
- Returning ORM objects from a service after `session.close()` is a design smell; return
  Pydantic schemas or plain dicts at the service boundary instead.

```python
# BEFORE — user.id accessed after session context exits → DetachedInstanceError
def create_user(data: dict) -> User:
    with Session(engine) as session:
        user = User(**data)
        session.add(user)
        session.commit()
    return user   # session closed; user.email now raises DetachedInstanceError

# AFTER option A — read inside session before close
def create_user(data: dict) -> dict:
    with Session(engine) as session:
        user = User(**data)
        session.add(user)
        session.commit()
        session.refresh(user)
        return {"id": user.id, "email": user.email}

# AFTER option B — disable expiry for short-lived sessions
Session = sessionmaker(engine, expire_on_commit=False)

def create_user(data: dict) -> User:
    with Session() as session:
        user = User(**data)
        session.add(user)
        session.commit()
        return user   # attributes still accessible; session is still open
```

### 8. Event Listeners Doing Business Logic
**Risk: 3**
**Smell:** AI puts business rules (sending emails, charging cards, updating audit logs) inside
`@event.listens_for(Model, "after_insert")`. This hides side effects, makes testing hard, and
couples the ORM layer to application concerns.
**Fix:** Move business logic to explicit service calls. Reserve event listeners for pure
ORM concerns (timestamps, slug generation, cascades the ORM cannot express natively).
**Safety checks:**
- Check if any tests rely on the listener firing for setup — they will need refactoring.
- `after_insert` runs inside the transaction; network calls here block the DB connection.
- If you must keep a listener (e.g., updated_at), make it a pure in-memory attribute set.

```python
# BEFORE — email sent from ORM event, untestable, blocks DB connection
from sqlalchemy import event

@event.listens_for(User, "after_insert")
def send_welcome_email(mapper, connection, target):
    email_client.send(target.email, "Welcome!")   # side effect in ORM layer

# AFTER — explicit service call at the application layer
class UserService:
    def create_user(self, data: dict) -> User:
        with Session(engine) as session:
            user = User(**data)
            session.add(user)
            session.commit()
            session.refresh(user)

        # explicit, visible, testable
        email_service.send_welcome(user.email)
        return user

# KEEP event listeners only for pure ORM concerns
@event.listens_for(User, "before_update")
def set_updated_at(mapper, connection, target):
    target.updated_at = datetime.utcnow()   # pure attribute mutation, no I/O
```

## FLASK PATTERNS

### 9. All Routes in `app.py` — No Blueprint Structure
**Risk: 3**
**Smell:** AI puts every route in a single `app.py` file. Works for toy apps, collapses at > 5
endpoints because imports, tests, and feature boundaries all tangle together.
**Fix:** Group routes into Blueprints by domain. Register blueprints on the app factory.
**Safety checks:**
- `url_prefix` must not conflict between blueprints.
- `url_for("users.create_user")` — blueprint name must prefix endpoint names in templates.
- Shared helpers (auth decorators, error handlers) go on the app, not a blueprint.

```python
# BEFORE — monolithic app.py
app = Flask(__name__)

@app.route("/users", methods=["GET"])
def list_users():
    ...

@app.route("/users/<int:id>", methods=["GET"])
def get_user(id):
    ...

@app.route("/orders", methods=["GET"])
def list_orders():
    ...

# AFTER — blueprints/users.py
from flask import Blueprint

users_bp = Blueprint("users", __name__, url_prefix="/users")

@users_bp.route("/", methods=["GET"])
def list_users():
    ...

@users_bp.route("/<int:id>", methods=["GET"])
def get_user(id: int):
    ...

# app.py — factory only
def create_app(config_object: str = "config.ProductionConfig") -> Flask:
    app = Flask(__name__)
    app.config.from_object(config_object)

    from .blueprints.users import users_bp
    from .blueprints.orders import orders_bp
    app.register_blueprint(users_bp)
    app.register_blueprint(orders_bp)

    return app
```

### 10. Business Logic in Route Handlers
**Risk: 3**
**Smell:** Route functions query the database, run business rules, send emails, and return responses
all in one place. Untestable without a real HTTP request.
**Fix:** Route handlers are thin: parse input → call service → shape response. Business logic
lives in a service layer that has no Flask imports.
**Safety checks:**
- Service functions must not import `request`, `g`, or any Flask context object.
- Service functions must be unit-testable with plain function calls (no test client needed).
- Validation belongs in WTForms, marshmallow, or Pydantic schemas — not in `if` chains in the route.

```python
# BEFORE — route doing everything
@users_bp.route("/", methods=["POST"])
def create_user():
    data = request.get_json()
    if not data.get("email"):
        return jsonify({"error": "email required"}), 400
    if User.query.filter_by(email=data["email"]).first():
        return jsonify({"error": "email taken"}), 409
    user = User(email=data["email"], name=data["name"])
    db.session.add(user)
    db.session.commit()
    send_welcome_email(user.email)
    return jsonify({"id": user.id}), 201

# AFTER — thin route + service layer
# services/user_service.py (no Flask imports)
class UserService:
    def create_user(self, email: str, name: str) -> User:
        if not email:
            raise ValueError("email required")
        if User.query.filter_by(email=email).first():
            raise DuplicateEmailError(email)
        user = User(email=email, name=name)
        db.session.add(user)
        db.session.commit()
        send_welcome_email(user.email)
        return user

# blueprints/users.py
@users_bp.route("/", methods=["POST"])
def create_user():
    data = request.get_json(force=True)
    try:
        user = user_service.create_user(email=data["email"], name=data["name"])
    except KeyError as e:
        return jsonify({"error": f"missing field: {e}"}), 400
    except DuplicateEmailError as e:
        return jsonify({"error": str(e)}), 409
    return jsonify({"id": user.id}), 201
```

### 11. Missing Error Handlers
**Risk: 3**
**Smell:** AI omits `@app.errorhandler` registrations. Flask returns HTML error pages by default;
API clients receive HTML they cannot parse. Unhandled exceptions return 500 with a stack trace
in production.
**Fix:** Register handlers for at least 400, 404, 405, 422, and 500. Return JSON for APIs.
**Safety checks:**
- `@app.errorhandler(Exception)` catches everything including `SystemExit` — use `HTTPException`
  as the catch-all base for Werkzeug errors.
- In debug mode Flask still shows the debugger; handlers only fire in production (`DEBUG=False`).
- Log the exception in the 500 handler before returning the response.

```python
# BEFORE — no error handlers; clients get HTML 404 pages
app = Flask(__name__)

# AFTER — JSON error responses for all common cases
from flask import jsonify
from werkzeug.exceptions import HTTPException

@app.errorhandler(HTTPException)
def handle_http_error(e: HTTPException):
    return jsonify({"error": e.name, "description": e.description}), e.code

@app.errorhandler(404)
def not_found(e):
    return jsonify({"error": "not found"}), 404

@app.errorhandler(405)
def method_not_allowed(e):
    return jsonify({"error": "method not allowed"}), 405

@app.errorhandler(500)
def internal_error(e):
    app.logger.exception("Unhandled exception")
    return jsonify({"error": "internal server error"}), 500
```

### 12. `g` Object Misuse — Storing DB Sessions Incorrectly
**Risk: 4**
**Smell:** AI stores a database session on `g` without proper teardown, or stores it under a
generic key that collides across blueprints. Also: storing non-request-scoped state on `g`.
**Fix:** Use `g` only for per-request objects. Tear down in `@app.teardown_appcontext`.
**Safety checks:**
- `g` is request-scoped in Flask (one per request context). Do not share across requests.
- `teardown_appcontext` receives an exception argument — always close the session even on error.
- Prefer explicit dependency passing over `g` for testability.

```python
# BEFORE — session stored with no teardown; leaks connections
@app.before_request
def open_db():
    g.db = Session(engine)

@users_bp.route("/<int:id>")
def get_user(id: int):
    user = g.db.get(User, id)   # session never closed on exception
    return jsonify({"name": user.name})

# AFTER — session on g with guaranteed teardown
@app.before_request
def open_db():
    g._db_session = Session(engine)

def get_db() -> Session:
    if not hasattr(g, "_db_session"):
        g._db_session = Session(engine)
    return g._db_session

@app.teardown_appcontext
def close_db(exception: BaseException | None) -> None:
    session = g.pop("_db_session", None)
    if session is not None:
        session.close()

@users_bp.route("/<int:id>")
def get_user(id: int):
    user = get_db().get(User, id)
    return jsonify({"name": user.name})
```

### 13. Missing Application Factory — Untestable App
**Risk: 4**
**Smell:** `app = Flask(__name__)` at module level with config applied immediately. Tests cannot
create isolated instances with different configs (e.g., test database URL).
**Fix:** Wrap everything in `create_app(config=None)`. Tests call `create_app("config.TestingConfig")`.
**Safety checks:**
- Ensure `db.init_app(app)` and all extension `.init_app()` calls are inside the factory.
- Tests must call `app.app_context().push()` or use `app.test_client()` as a context manager.
- `current_app` proxy works once the app context is active — never access it at import time.

```python
# BEFORE — module-level app, impossible to swap test config
app = Flask(__name__)
app.config["SQLALCHEMY_DATABASE_URI"] = os.getenv("DATABASE_URL")
db = SQLAlchemy(app)

# AFTER — factory pattern
# extensions.py
from flask_sqlalchemy import SQLAlchemy
db = SQLAlchemy()   # no app bound yet

# app.py
def create_app(config_object: str = "config.ProductionConfig") -> Flask:
    app = Flask(__name__)
    app.config.from_object(config_object)

    db.init_app(app)

    from .blueprints.users import users_bp
    app.register_blueprint(users_bp)

    return app

# conftest.py — tests get their own isolated app
@pytest.fixture(scope="session")
def app():
    return create_app("config.TestingConfig")

@pytest.fixture()
def client(app):
    return app.test_client()
```

### 14. Config Not Using `from_object` or `from_envvar`
**Risk: 3**
**Smell:** AI sets config keys with individual `app.config["KEY"] = os.getenv("KEY")` lines
scattered through the file. Env vars are read at import time, not at app creation time. Test
overrides are fragile.
**Fix:** Use typed config classes with `from_object`. Read env vars inside the class body.
**Safety checks:**
- Secrets must never be committed. Config classes should pull from `os.environ` with no defaults
  for required secrets, raising `KeyError` at startup if missing.
- `from_envvar` points to a file path; `from_object` points to a dotted class path.

```python
# BEFORE — scattered, untestable config
app = Flask(__name__)
app.config["SECRET_KEY"] = os.getenv("SECRET_KEY", "dev-secret")
app.config["SQLALCHEMY_DATABASE_URI"] = os.getenv("DATABASE_URL")
app.config["DEBUG"] = os.getenv("DEBUG", "false").lower() == "true"

# AFTER — config classes
# config.py
class BaseConfig:
    SECRET_KEY: str = os.environ["SECRET_KEY"]        # raises if missing
    SQLALCHEMY_TRACK_MODIFICATIONS = False
    DEBUG = False

class DevelopmentConfig(BaseConfig):
    DEBUG = True
    SQLALCHEMY_DATABASE_URI = os.environ.get("DATABASE_URL", "sqlite:///dev.db")

class TestingConfig(BaseConfig):
    TESTING = True
    SQLALCHEMY_DATABASE_URI = "sqlite:///:memory:"
    SECRET_KEY = "test-secret-not-used-in-prod"       # safe for test-only

class ProductionConfig(BaseConfig):
    SQLALCHEMY_DATABASE_URI = os.environ["DATABASE_URL"]  # hard fail if missing

# app.py
def create_app(config_object: str = "config.ProductionConfig") -> Flask:
    app = Flask(__name__)
    app.config.from_object(config_object)
    return app
```

### 15. Circular Imports Between Blueprints and Models
**Risk: 3**
**Smell:** `models.py` imports a blueprint for a URL helper; blueprint imports `models.py` for
the ORM class. Python raises `ImportError: cannot import name X` at startup.
**Fix:** Organise imports so models never import from blueprints. Use `url_for` with string
names, not imported views.
**Safety checks:**
- `db` (the SQLAlchemy extension) must live in a module that neither blueprints nor models
  import from in a circular way. Typically `extensions.py`.
- Import blueprints inside `create_app()`, not at module top level.
- Use `flask shell` to quickly verify import order.

```python
# BEFORE — circular: models.py imports users_bp for url_for
# models.py
from blueprints.users import users_bp    # circular
class User(db.Model):
    ...
    def profile_url(self):
        return url_for("users.get_user", id=self.id)

# AFTER — models have zero blueprint imports
# models.py
from extensions import db

class User(db.Model):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255))

    # URL generation pushed to the view or a separate presenter layer
    # models.py knows nothing about blueprints

# extensions.py (imported by both models and blueprints without circularity)
from flask_sqlalchemy import SQLAlchemy
db = SQLAlchemy()
```

### 16. Synchronous DB Calls Blocking in Async Flask
**Risk: 4**
**Smell:** When using `async def` route handlers with `Flask[2.0+]` + `asgiref` or Quart,
AI still calls synchronous SQLAlchemy (or `psycopg2` / `pymysql`) inside `async def` functions.
This blocks the event loop thread.
**Fix:** Either stay synchronous (Flask's default threading model) or switch to fully async
stack (Quart + `asyncpg` + SQLAlchemy async).
**Safety checks:**
- Mixing `async def` routes with synchronous DB drivers is the worst of both worlds.
- If you don't need async, remove all `async def` from routes — Flask handles concurrency via threads.
- If you do need async, use `asyncpg` + `SQLAlchemy[asyncio]` + Quart (not Flask).

```python
# BEFORE — async route with blocking synchronous DB call
@app.route("/users/<int:id>")
async def get_user(id: int):
    # session.get() calls psycopg2 synchronously — blocks event loop
    user = db.session.get(User, id)
    return jsonify({"name": user.name})

# AFTER option A — drop async, use Flask's thread model (simplest)
@app.route("/users/<int:id>")
def get_user(id: int):
    user = db.session.get(User, id)
    return jsonify({"name": user.name})

# AFTER option B — full async with Quart + asyncpg + SQLAlchemy async
# quart_app.py
from quart import Quart, jsonify
from sqlalchemy.ext.asyncio import AsyncSession, create_async_engine

engine = create_async_engine("postgresql+asyncpg://...")

@app.route("/users/<int:id>")
async def get_user(id: int):
    async with AsyncSession(engine) as session:
        user = await session.get(User, id)
        return jsonify({"name": user.name})
```

## FASTAPI PATTERNS

### 17. DB Sessions Created Outside `Depends()`
**Risk: 5**
**Smell:** AI creates an `AsyncSession` or `Session` at the top of a route handler instead of
injecting it via FastAPI's dependency system. The session is not closed on exception paths,
and cannot be overridden in tests.
**Fix:** Yield the session from a `Depends()` generator. FastAPI's DI handles cleanup.
**Safety checks:**
- The generator must `yield` (not `return`) so FastAPI runs teardown after the response.
- Use `try/except/finally` in the generator if you need to rollback on error.
- Override the dependency in tests with `app.dependency_overrides`.

```python
# BEFORE — session created inside handler, no cleanup on error
@router.get("/users/{id}")
async def get_user(id: int):
    session = AsyncSession(engine)          # never closed on exception
    user = await session.get(User, id)
    await session.close()
    return user

# AFTER — session via Depends() with guaranteed cleanup
from sqlalchemy.ext.asyncio import AsyncSession
from fastapi import Depends

async def get_session() -> AsyncGenerator[AsyncSession, None]:
    async with AsyncSession(engine) as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

@router.get("/users/{id}", response_model=UserSchema)
async def get_user(id: int, session: AsyncSession = Depends(get_session)):
    user = await session.get(User, id)
    if user is None:
        raise HTTPException(status_code=404, detail="User not found")
    return user
```

### 18. Route Handlers Doing Everything
**Risk: 3**
**Smell:** FastAPI route handler validates input manually, queries the DB, applies business rules,
sends notifications, and shapes the response — all in one function. Identical to Flask pattern 10.
**Fix:** Thin handler → service layer → repository layer.
**Safety checks:**
- Service functions must not import `Request`, `Depends`, or any FastAPI symbol.
- Each layer must be independently testable with plain `pytest` (no `TestClient`).

```python
# BEFORE — monolithic handler
@router.post("/users/")
async def create_user(data: dict, session: AsyncSession = Depends(get_session)):
    if not data.get("email"):
        raise HTTPException(400, "email required")
    existing = await session.execute(select(User).where(User.email == data["email"]))
    if existing.scalar_one_or_none():
        raise HTTPException(409, "email taken")
    user = User(**data)
    session.add(user)
    await session.commit()
    await email_client.send_welcome(user.email)
    return {"id": user.id, "email": user.email}

# AFTER — handler delegates to service
# services/user_service.py
class UserService:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def create_user(self, email: str, name: str) -> User:
        if await self._email_exists(email):
            raise DuplicateEmailError(email)
        user = User(email=email, name=name)
        self.session.add(user)
        await self.session.flush()   # get user.id without committing
        await email_client.send_welcome(email)
        return user

    async def _email_exists(self, email: str) -> bool:
        result = await self.session.execute(select(User).where(User.email == email))
        return result.scalar_one_or_none() is not None

# routers/users.py
@router.post("/users/", response_model=UserResponse, status_code=201)
async def create_user(
    payload: CreateUserRequest,
    session: AsyncSession = Depends(get_session),
):
    service = UserService(session)
    try:
        user = await service.create_user(email=payload.email, name=payload.name)
    except DuplicateEmailError:
        raise HTTPException(status_code=409, detail="email already in use")
    return user
```

```python
# BEFORE — returns ORM object, serialises everything including password_hash
@router.get("/users/{id}")
```

### 20. `Depends()` with Mutable Default Arguments
**Risk: 3**
**Smell:** AI writes `def get_items(filters: dict = {})` or `def route(tags: list = [])` in
dependency signatures. Python shares a single mutable object across all calls.
**Fix:** Use `None` as the default; create the mutable inside the function body. Or use
Pydantic models for complex query parameters.
**Safety checks:**
- This is a Python language bug, not FastAPI-specific, but FastAPI Depends functions are called
  per-request so the mutable accumulates across requests.
- Use `Query(None)` for typed optional query params instead of raw defaults.

```python
# BEFORE — shared mutable default
@router.get("/items/")
async def list_items(filters: dict = {}):   # same dict object every request

@router.get("/items/")
async def list_items(filters: dict | None = None):
    resolved = filters or {}

    return await get_items(resolved)

# AFTER option B — typed query params with Pydantic (preferred)
class ItemFilters(BaseModel):
    limit: int = 50
    offset: int = 0
    status: str | None = None

@router.get("/items/")
```

### 21. Lifespan / Startup Events Doing Blocking I/O
**Risk: 4**
**Smell:** AI puts database migrations, heavy model loading, or HTTP requests inside
`@app.on_event("startup")` or the `lifespan` context using synchronous calls.
Blocks the event loop during startup; the newer `lifespan` pattern is also frequently
implemented incorrectly (missing `yield`).
**Fix:** Use the `lifespan` context manager with `async with`; run blocking I/O in a thread
via `asyncio.to_thread`.
**Safety checks:**
- `@app.on_event` is deprecated in FastAPI 0.93+; use `@asynccontextmanager` lifespan.
- Alembic migrations are synchronous — run them via `asyncio.to_thread` or as a pre-start script.
- The lifespan generator must `yield` exactly once; code after `yield` is teardown.

```python
# BEFORE — blocking startup and deprecated decorator
@app.on_event("startup")
def startup():
    run_migrations()          # synchronous, blocks event loop
    load_ml_model()           # heavy synchronous I/O

# AFTER — async lifespan with blocking work offloaded
from contextlib import asynccontextmanager
import asyncio

@asynccontextmanager
async def lifespan(app: FastAPI):
    # startup
    await asyncio.to_thread(run_migrations)    # sync alembic in thread
    app.state.model = await asyncio.to_thread(load_ml_model)
    yield
    # teardown
    await engine.dispose()

app = FastAPI(lifespan=lifespan)
```

### 22. `BackgroundTasks` for Work Needing Guaranteed Execution
**Risk: 5**
**Smell:** AI uses FastAPI's `BackgroundTasks` to send emails, charge payments, or update
external systems. `BackgroundTasks` runs in the same process with no persistence. If the process
crashes before the task runs, the work is silently lost.
**Fix:** Use Celery (or ARQ / RQ) for any background work that must not be lost. Reserve
`BackgroundTasks` only for fire-and-forget logging or cache invalidation that can be dropped.
**Safety checks:**
- `BackgroundTasks` tasks run after the response is sent, in the same event loop.
- No retry, no persistence, no visibility — not suitable for financial or user-facing operations.
- If the task fails, the error is logged but the user never knows.

```python
# BEFORE — payment processed in BackgroundTasks; silently lost on crash
@router.post("/orders/", status_code=202)
async def create_order(
    payload: CreateOrderRequest,
    background_tasks: BackgroundTasks,
    session: AsyncSession = Depends(get_session),
):
    order = await order_service.create(session, payload)
    background_tasks.add_task(charge_card, order.id)   # lost if process dies
    return {"order_id": order.id}

# AFTER — durable task via Celery
from celery_app import charge_card_task

@router.post("/orders/", status_code=202)
async def create_order(
    payload: CreateOrderRequest,
    session: AsyncSession = Depends(get_session),
):
    order = await order_service.create(session, payload)
    charge_card_task.delay(order.id)   # persisted to broker, retryable
    return {"order_id": order.id}

# KEEP BackgroundTasks only for disposable work
@router.post("/events/")
async def track_event(payload: EventPayload, background_tasks: BackgroundTasks):
    background_tasks.add_task(analytics.track, payload.dict())  # loss acceptable
    return {"status": "ok"}
```

### 24. Pydantic Model as Both Input Schema and ORM Model
**Risk: 3**
**Smell:** AI creates a single Pydantic model used for HTTP request parsing, response serialization,
and ORM mapping. Input fields (password plaintext), internal fields (password_hash), and output
fields (created_at) are all on one class, creating tight coupling and security holes.
**Fix:** Separate concerns: `CreateUserRequest` (input), `UserResponse` (output), `User` (ORM model).
**Safety checks:**
- Input schemas must never include fields that only the server sets (id, created_at, password_hash).
- Output schemas must never expose fields clients should not see (password_hash, internal flags).
- ORM models and Pydantic schemas are different layers — they evolve at different rates.

```python
# BEFORE — one model for everything
class User(BaseModel):
    id: int | None = None
    email: str
    name: str
    password: str                # plaintext in request AND response
    password_hash: str | None = None
    created_at: datetime | None = None
    is_admin: bool = False       # client-controlled privilege escalation risk

# AFTER — three separate models
class CreateUserRequest(BaseModel):
    email: EmailStr
    name: str
    password: str = Field(min_length=8)   # input only; never returned

class UserResponse(BaseModel):
    id: int
    email: str
    name: str
    created_at: datetime
    # no password, no password_hash, no is_admin

    model_config = ConfigDict(from_attributes=True)

class User(Base):   # ORM model — not a Pydantic model
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    email: Mapped[str] = mapped_column(String(255), unique=True, index=True)
    name: Mapped[str] = mapped_column(String(255))
    password_hash: Mapped[str] = mapped_column(String(255))
    is_admin: Mapped[bool] = mapped_column(Boolean, default=False)
    created_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow)
```

### 25. `Optional` Fields With No Default — Ambiguous None vs Missing
**Risk: 2**
**Smell:** AI writes `field: Optional[str]` (or `str | None`) with no default value. The field
is required (client must send it) but accepts `null`. This conflates "not provided" with
"explicitly null", which usually have different semantics in PATCH endpoints.
**Fix:** Make the intent explicit: required nullable (`field: str | None`), optional with default
(`field: str | None = None`), or use `Unset` sentinel for PATCH semantics.
**Safety checks:**
- On POST, a required `str | None` means the client must send the key (even if null) — unusual.
- On PATCH, use `model.model_dump(exclude_unset=True)` to detect truly missing fields.
- Pydantic V2 distinguishes `None` from missing via `model_fields_set`.

```python
# BEFORE — ambiguous: is this required? does None mean "clear the field"?
class UpdateUserRequest(BaseModel):
    name: Optional[str]     # required but nullable — almost never correct
    email: Optional[str]    # same problem

# AFTER — explicit intent per field
class UpdateUserRequest(BaseModel):
    # All fields optional for PATCH (not sent = don't update)
    name: str | None = None      # None = "clear the name"; absent = "don't touch"
    email: str | None = None

    # Use exclude_unset to distinguish None from absent
    def get_updates(self) -> dict:
        return self.model_dump(exclude_unset=True)

# In the handler:
@router.patch("/users/{id}", response_model=UserResponse)
async def update_user(id: int, payload: UpdateUserRequest, ...):
    updates = payload.get_updates()   # only fields the client actually sent
    if not updates:
        raise HTTPException(400, "no fields to update")
    await user_service.partial_update(id, updates)
```

### 26. Task Doing Business Logic Instead of Calling a Service
**Risk: 3**
**Smell:** AI writes all business logic directly inside the `@app.task` function. Logic cannot
be unit-tested without a Celery worker. Identical code is duplicated in synchronous paths.
**Fix:** Tasks are thin dispatchers. Business logic lives in service functions callable from
both web handlers and tasks.
**Safety checks:**
- Service functions must work without a Celery context (no `self`, no `current_task`).
- Test the service function directly; test the task only for retry/error behaviour.

```python
# BEFORE — business logic trapped inside task
@celery.task
def process_order(order_id: int):
    order = db.session.get(Order, order_id)
    if order.status != "pending":
        return
    inventory.deduct(order.items)
    payment.charge(order.total)
    order.status = "confirmed"
    email.send_confirmation(order.user.email)
    db.session.commit()

# AFTER — task delegates to service
@celery.task(bind=True, max_retries=3, acks_late=True)
def process_order(self, order_id: int):
    try:
        order_service.process(order_id)
    except TransientError as e:
        raise self.retry(exc=e, countdown=2 ** self.request.retries)

# services/order_service.py — testable with plain pytest
def process(order_id: int) -> None:

        order = session.get(Order, order_id)
        if order is None or order.status != "pending":
            return
        inventory.deduct(session, order.items)
        payment.charge(order.total)
        order.status = "confirmed"
        session.commit()
    email.send_confirmation(order.user_email)
```

### 27. Non-Idempotent Tasks — No Check-and-Skip Pattern
**Risk: 5**
**Smell:** AI tasks perform side effects (charge a card, send an email, create a DB record)
without checking if the work was already done. With `acks_late=True` and broker redelivery,
tasks can run more than once, duplicating the side effect.
**Fix:** Add an idempotency check at the start of every task. Use a unique key in the DB or
cache to detect and skip duplicate runs.
**Safety checks:**
- Check-and-skip must be atomic to prevent TOCTOU races under concurrent task execution.
- Use `select_for_update()` or a unique DB constraint to enforce idempotency at the DB level.
- Idempotency keys should be tied to the business event, not the Celery task ID.

```python
# BEFORE — duplicate email sent if task retried
@celery.task(acks_late=True)
def send_welcome_email(user_id: int):
    user = User.query.get(user_id)
    email_client.send(user.email, "Welcome!")   # runs twice on redelivery

# AFTER — idempotent task with DB-level guard
@celery.task(bind=True, acks_late=True, max_retries=3)
def send_welcome_email(self, user_id: int):
    with Session(engine) as session:
        # Atomic check: only proceed if not already sent
        result = session.execute(
            update(User)
            .where(User.id == user_id, User.welcome_email_sent == False)
            .values(welcome_email_sent=True)
            .returning(User.email)
        )
        session.commit()
        row = result.fetchone()

    if row is None:
        return   # already sent or user not found — skip

    try:
        email_client.send(row.email, "Welcome!")
    except EmailServiceError as e:
        raise self.retry(exc=e, countdown=60)
```

### 28. Passing Complex Objects as Task Arguments
**Risk: 4**
**Smell:** AI passes ORM model instances, Pydantic objects, or large nested dicts as Celery
task arguments. These are serialised with `pickle` (security risk) or `json` (fails for non-JSON
types). The serialised object may be stale by the time the task runs.
**Fix:** Pass only primitive IDs and scalar values. Fetch fresh state from the DB inside the task.
**Safety checks:**
- Always use JSON serialiser: `CELERY_TASK_SERIALIZER = "json"`.
- If you must pass structured data, use a TypedDict or dataclass that serialises to a plain dict.
- Never pass `session`, `request`, or any context-bound object.

```python
# BEFORE — passing ORM model (pickle required, stale data risk)
@celery.task
def notify_user(user: User, message: str):   # User is an ORM object
    email_client.send(user.email, message)

# called with
notify_user.delay(user_object, "Your order is ready")   # serialises the entire User

# AFTER — pass primitive ID, fetch fresh inside task
@celery.task(bind=True, acks_late=True)
def notify_user(self, user_id: int, message: str):
    with Session(engine) as session:
        user = session.get(User, user_id)
        if user is None:
            return   # user deleted between enqueue and execution
        email_client.send(user.email, message)

# called with
notify_user.delay(user.id, "Your order is ready")
```

### 29. No `bind=True` + `self.retry()` for Transient Errors
**Risk: 4**
**Smell:** AI tasks either let exceptions propagate uncaught (task marked FAILURE immediately,
no retry) or catch all exceptions and swallow them silently. Transient failures (network timeouts,
rate limits) are not retried.
**Fix:** Use `bind=True` to get the task instance, catch specific transient exceptions,
and call `self.retry()` with exponential backoff.
**Safety checks:**
- Only retry on transient errors (network, rate limit, lock contention). Let permanent errors
  (bad data, programming errors) fail immediately.
- Set a `max_retries` cap to prevent infinite retry loops.
- `self.retry()` raises `Retry`, which must not be caught by a broad `except Exception`.

```python
# BEFORE — no retry; first transient error = permanent failure
@celery.task
def send_sms(phone: str, message: str):
    sms_client.send(phone, message)   # raises SMSRateLimit on 429

# BEFORE — swallows errors silently
@celery.task
def send_sms(phone: str, message: str):
    try:
        sms_client.send(phone, message)
    except Exception:
        pass   # silent failure — user never receives SMS

# AFTER — retry transient, fail fast on permanent
@celery.task(bind=True, max_retries=5, acks_late=True, default_retry_delay=30)
def send_sms(self, phone: str, message: str):
    try:
        sms_client.send(phone, message)
    except SMSRateLimit as e:
        # exponential backoff: 30s, 60s, 120s, 240s, 480s
        raise self.retry(exc=e, countdown=30 * (2 ** self.request.retries))
    except SMSInvalidNumber:
        # permanent — do not retry
        logger.error("Invalid phone number: %s", phone)
        raise
```

### 30. Missing `acks_late=True` for At-Least-Once Delivery
**Risk: 4**
**Smell:** Default Celery behaviour acknowledges a task immediately when it is picked up by a worker
(`acks_early`). If the worker crashes mid-execution, the task is lost. AI almost never sets `acks_late`.
**Fix:** Set `acks_late=True` on tasks that must not be silently dropped. Combine with
`reject_on_worker_lost=True` to re-queue on worker crash.
**Safety checks:**
- `acks_late=True` requires tasks to be idempotent — the task may run more than once (see pattern 27).
- Enabling late acks globally via `CELERY_ACKS_LATE = True` is simpler but applies to all tasks.
- For truly fire-and-forget tasks (analytics, cache warming), `acks_early` is fine.

```python
# BEFORE — acks early (default); lost on worker crash
@celery.task
def process_payment(order_id: int):
    payment_gateway.charge(order_id)   # worker crashes here → task lost, no charge, no retry

# AFTER — acks late + idempotency guard
@celery.task(
    bind=True,
    acks_late=True,
    reject_on_worker_lost=True,
    max_retries=3,
)
def process_payment(self, order_id: int):
    with Session(engine) as session:
        # Idempotency: only charge if not already charged
        order = session.execute(
            select(Order).where(Order.id == order_id).with_for_update()
        ).scalar_one_or_none()

        if order is None or order.payment_status == "charged":
            return

        try:
            payment_gateway.charge(order.total, order.payment_token)
        except GatewayTimeout as e:
            raise self.retry(exc=e, countdown=60)

        order.payment_status = "charged"
        session.commit()
```

### 31. Task Chains Without Error Handling
**Risk: 4**
**Smell:** AI creates Celery chains where a failure in step N silently stops execution of steps
N+1…N+k with no notification, no cleanup, and no partial-completion handling.
**Fix:** Add a `link_error` callback to the chain. Use `chord` error callbacks for parallel groups.
**Safety checks:**
- Error callbacks receive the task ID and exception info, not the original arguments — fetch
  context from the DB using the task ID or a separate tracking record.
- `on_error` in `chain` is not the same as `link_error` — verify which Celery version API you target.
- Consider saga/compensating transactions for chains with external side effects.

```python
# BEFORE — chain with no error handling
from celery import chain

result = chain(
    validate_order.s(order_id),
    reserve_inventory.s(),
    charge_payment.s(),
    send_confirmation.s(),
).apply_async()
# if charge_payment fails, inventory is reserved but payment never processed → inconsistent state

# AFTER — chain with error callback and compensating logic
from celery import chain
from celery.utils.log import get_task_logger

logger = get_task_logger(__name__)

@celery.task
def handle_order_failure(order_id: int, reason: str):
    logger.error("Order %s failed: %s", order_id, reason)
    with Session(engine) as session:
        order = session.get(Order, order_id)
        if order:
            order.status = "failed"
            order.failure_reason = reason
            session.commit()
    inventory_service.release_reservation(order_id)    # compensate
    email_service.send_failure_notice(order_id)

# use .on_error() for the entire chain
pipeline = (
    validate_order.s(order_id)
    | reserve_inventory.s()
    | charge_payment.s()
    | send_confirmation.s()
).on_error(handle_order_failure.s(order_id, "pipeline_failed"))

pipeline.apply_async()
```

### 32. `setup_method` Doing DB Writes for Every Test
**Risk: 3**
**Smell:** AI puts database setup inside `setup_method` (or `setUp` in unittest style). This
runs before every single test method, makes the test suite slow, and does not allow fixture
sharing across tests in the same class.
**Fix:** Use `pytest` fixtures with appropriate scope (`function`, `class`, `module`, `session`).
Use `scope="module"` or `scope="session"` for expensive setup that does not mutate state.
**Safety checks:**
- `scope="session"` fixtures are shared across the entire test run — do not mutate shared state.
- Use `scope="function"` + transactions that roll back after each test for DB isolation.
- `autouse=True` fixtures apply to all tests in scope without explicit request.

```python
# BEFORE — setup_method runs full DB insert for every test
class TestUserService:
    def setup_method(self):
        self.db = create_test_db()
        self.user = User(email="test@example.com", name="Test")
        self.db.session.add(self.user)
        self.db.session.commit()   # one INSERT per test

    def test_get_user(self): ...
    def test_update_user(self): ...
    def test_delete_user(self): ...   # 3× INSERT overhead

# AFTER — fixture with appropriate scope
# conftest.py
@pytest.fixture(scope="session")
def engine():
    return create_engine("sqlite:///:memory:")

@pytest.fixture(scope="session")
def tables(engine):
    Base.metadata.create_all(engine)
    yield
    Base.metadata.drop_all(engine)

@pytest.fixture()
def session(engine, tables):
    connection = engine.connect()
    transaction = connection.begin()
    session = Session(bind=connection)
    yield session
    session.close()
    transaction.rollback()   # rollback after each test — no leftover data
    connection.close()

@pytest.fixture()
def user(session):
    u = User(email="test@example.com", name="Test")
    session.add(u)
    session.flush()   # get u.id without committing
    return u

class TestUserService:
    def test_get_user(self, user, session): ...      # fixtures injected
    def test_update_user(self, user, session): ...
    def test_delete_user(self, user, session): ...   # each test gets a clean slate
```

### 33. Deep Fixture Chains — Fixtures Calling Fixtures Calling Fixtures
**Risk: 2**
**Smell:** AI creates fixture chains 5+ levels deep where understanding a single test requires
reading 6 files. `conftest.py` fixtures call other fixtures that call others, making setup
invisible and debugging nightmarish.
**Fix:** Keep fixture chains to 3 levels maximum. Prefer explicit factory functions (`make_user(...)`)
over deeply composed fixtures. Use fixtures for infrastructure, factories for data.
**Safety checks:**
- If you must trace > 3 fixtures to understand what a test receives, flatten the chain.

### 34. Missing `parametrize` — Copy-Paste Test Functions
**Risk: 2**
**Smell:** AI generates identical test functions differing only in the input value and expected
output, instead of using `@pytest.mark.parametrize`. Five nearly identical functions for five
edge cases.
**Fix:** Collapse into one parametrized test. Name cases with `ids` for readable failure messages.
**Safety checks:**
- Each parametrize case gets its own test ID in the output — use `ids=` to make them readable.
- Parametrize can be stacked for combinatorial tests (`@pytest.mark.parametrize` × 2).
- If setup differs significantly between cases, parametrize is wrong — keep separate tests.

```python
# BEFORE — copy-paste tests, one per value
```

### 35. Over-Mocking with `unittest.mock.patch` — Sign of Bad DI
**Risk: 3**
**Smell:** AI patches module-level functions and class methods extensively because the code under
test has hard-coded dependencies. `@patch("myapp.services.user_service.email_client.send")` in
every test means the dependency is not injectable.
**Fix:** Use dependency injection so tests pass fake implementations directly. Reserve `patch`
for third-party libraries you genuinely cannot inject.
**Safety checks:**
- If you need more than 2 `@patch` decorators on a test, refactor the code under test.
- `patch` tests the implementation path (what function was called), not the behaviour (what changed).
- Fake/stub objects are more readable and refactor-safe than patch strings.

```python
# BEFORE — patching because email_client is a hard-coded import
# services/user_service.py
import email_client   # hard-coded dependency

def create_user(data: dict) -> User:
    user = User(**data)
    email_client.send(user.email, "Welcome!")    # cannot inject a fake
    return user

# test_user_service.py
@patch("myapp.services.user_service.email_client.send")
@patch("myapp.services.user_service.db.session.commit")
@patch("myapp.services.user_service.db.session.add")
def test_create_user(mock_add, mock_commit, mock_send):
    create_user({"email": "a@b.com", "name": "Alice"})
    mock_send.assert_called_once()   # testing implementation, not behaviour

# AFTER — inject dependencies, no patching needed
# services/user_service.py
class UserService:
    def __init__(self, session: Session, email_client: EmailClient):
        self.session = session
        self.email_client = email_client

    def create_user(self, email: str, name: str) -> User:
        user = User(email=email, name=name)
        self.session.add(user)
        self.session.flush()
        self.email_client.send(email, "Welcome!")
        return user

# test_user_service.py
class FakeEmailClient:
    def __init__(self): self.sent = []
    def send(self, to, body): self.sent.append((to, body))

def test_create_user(session):
    email_client = FakeEmailClient()
    service = UserService(session=session, email_client=email_client)
    user = service.create_user("a@b.com", "Alice")
    assert user.email == "a@b.com"
    assert ("a@b.com", "Welcome!") in email_client.sent   # behaviour, not implementation
```

### 36. Testing Implementation, Not Behaviour
**Risk: 3**
**Smell:** Tests assert on internal state (which method was called, which SQL was executed,
which internal variable was set) rather than on observable outcomes (what did the user see,
what is in the DB, what was returned).
**Fix:** Assert on the public contract of the unit: return values, DB state, and side effects
visible to the caller.
**Safety checks:**
- If a test breaks when you refactor without changing behaviour, it is testing implementation.
- `mock.assert_called_with(...)` is almost always an implementation test.
- Prefer DB state assertions (`session.get(User, id)`) over call assertions.

```python
# BEFORE — tests that an internal method was called with specific args
def test_create_user_calls_repo(mocker):
    mock_repo = mocker.patch("services.user_repo.create")
    user_service.create_user({"email": "a@b.com"})
    mock_repo.assert_called_once_with(email="a@b.com")   # tests internals

# AFTER — tests the observable outcome
def test_create_user_persists_to_db(session):
    service = UserService(session)
    user = service.create_user(email="a@b.com", name="Alice")

    persisted = session.get(User, user.id)
    assert persisted is not None
    assert persisted.email == "a@b.com"
    assert persisted.name == "Alice"
    # refactor service internals freely — this test still passes
```

### 37. Missing `conftest.py` Organisation — Fixtures Scattered Everywhere
**Risk: 2**
**Smell:** AI puts fixtures in individual test files. Tests in other files cannot reuse them.
The same fixture is defined multiple times across the test suite with slight variations,
diverging over time.
**Fix:** Centralise shared fixtures in `conftest.py` files at the appropriate level of the
directory tree. Module-specific fixtures stay in the module's `conftest.py`.
**Safety checks:**
- `conftest.py` is automatically discovered by pytest — no import needed.
- Place infrastructure fixtures (engine, session, app) in the root `conftest.py`.
- Place domain-specific factories (make_user, make_order) in domain subdirectory `conftest.py` files.

```
# BEFORE — scattered fixtures, no sharing
tests/
  test_users.py      ← defines db_session, make_user
  test_orders.py     ← redefines db_session, defines make_order (uses a different make_user)
  test_payments.py   ← redefines everything from scratch

# AFTER — organised conftest hierarchy
tests/
  conftest.py        ← engine, session, app, client (shared by everything)
  users/
    conftest.py      ← make_user factory (used by user AND order tests)
    test_users.py
  orders/
    conftest.py      ← make_order factory (depends on make_user from parent)
    test_orders.py
  payments/
    conftest.py      ← make_payment factory
    test_payments.py
```

```python
# tests/conftest.py — infrastructure only
@pytest.fixture(scope="session")
def engine():
    return create_engine("sqlite:///:memory:")

@pytest.fixture()
def session(engine):
    with Session(engine) as s:
        yield s

# tests/users/conftest.py — domain factory
@pytest.fixture()
def make_user(session):
    def _factory(email="u@example.com", **kwargs):
        u = User(email=email, **kwargs)
        session.add(u)
        session.flush()
        return u
    return _factory

# tests/orders/conftest.py — uses parent factory without reimplementing it
@pytest.fixture()
def make_order(session, make_user):   # make_user from tests/users/conftest.py
    def _factory(user=None, **kwargs):
        u = user or make_user()
        o = Order(user_id=u.id, **kwargs)
        session.add(o)
        session.flush()
        return o
    return _factory
```

### 38. `assert` on Every Attribute Instead of `assert obj == expected`
**Risk: 1**
**Smell:** AI generates 10 individual `assert user.name == "Alice"`, `assert user.email == "..."`,
`assert user.role == "..."` lines instead of comparing against an expected object. Fails at the
first broken attribute and hides all other failures.
**Fix:** Assert against a full expected value. Use dataclasses or Pydantic models for structured
comparison. Or use `pytest`'s `assert` introspection on dicts.
**Safety checks:**
- Make sure `__eq__` is defined (or that you compare dicts) before using equality assertions.
- SQLAlchemy ORM instances do not implement `__eq__` by default — compare dicts or Pydantic schemas.
- For partial checks (only a subset of fields), use `assert {k: getattr(obj, k) for k in fields} == expected_subset`.

```python
# BEFORE — one assert per attribute; hides all failures after the first
def test_create_user(session):
    user = user_service.create_user("alice@example.com", "Alice", "admin")
    assert user.email == "alice@example.com"   # stops here if wrong
    assert user.name == "Alice"
    assert user.role == "admin"
    assert user.active is True
    assert user.created_at is not None

# AFTER option A — compare dict (works without __eq__)
def test_create_user(session):
    user = user_service.create_user("alice@example.com", "Alice", "admin")
    assert {
        "email": user.email,
        "name": user.name,
        "role": user.role,
        "active": user.active,
    } == {
        "email": "alice@example.com",
        "name": "Alice",
        "role": "admin",
        "active": True,
    }
    # pytest shows the full diff on failure — all broken fields visible at once

# AFTER option B — compare against Pydantic schema (most readable)
expected = UserResponse(
    id=user.id,
    email="alice@example.com",
    name="Alice",
    role="admin",
    active=True,
)
assert UserResponse.model_validate(user) == expected
```
